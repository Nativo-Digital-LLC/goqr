## Regla de congelamiento

- `establishments/{id}.billing.priceLock = { plan, dop, usd }` es el precio que paga ese cliente.
- Monto efectivo = `priceLock` si `priceLock.plan === plan`; si no (o no existe, o está mal formado), el de lista (`PLANS`).
  Misma función en los dos repos: `effectivePrice` en `functions/src/modules/plans.ts` y en `src/lib/billing.ts`.
- Se escribe al activar un plan:
  - Checkout con tarjeta: `createCheckoutSession` cobra `effectivePrice(...)` y lo manda en `metadata.priceDop`; el webhook `checkout.session.completed` lo guarda como `priceLock`.
  - Transferencia aprobada / "Marcar pagado": `approvalPatch` guarda `effectivePrice(billing, plan)`.
- Consecuencia: cada cliente nuevo queda congelado al precio de lista del día en que activó. Una futura subida no lo afecta salvo que se le borre o cambie el `priceLock`.
- Cambiar de plan (p. ej. mensual 300 → anual) toma el precio de lista del plan nuevo.
- Lo usan: checkout (Stripe `price_data`), monto esperado de transferencias, factura de "Marcar pagado", MRR del admin, "Tu plan", selector de plan, página de transferencia y resultado del checkout.

## Migración mínima (antes de desplegar Functions)

Orden importa: si se despliega primero y se aprueba una transferencia de un cliente sin `priceLock`, queda congelado en 500.

1. Identificar los 5 clientes que pagan RD$300 (admin → Clientes, o en Firestore: `billing.plan == 'monthly'` con pagos de 300 en `bills`). Anotar sus `establishmentId`.
2. Escribirles el lock (script con firebase-admin, credenciales de producción):

   ```ts
   const LEGACY_300 = ['<establishmentId1>', '<establishmentId2>', '<establishmentId3>', '<establishmentId4>', '<establishmentId5>'];
   for (const id of LEGACY_300) {
   	await db.collection('establishments').doc(id).update({ 'billing.priceLock': { plan: 'monthly', dop: 300, usd: 5 } });
   }
   ```

3. Verificar en Firestore que los 5 documentos tienen `billing.priceLock.dop == 300`.
4. Desplegar Functions y luego la web.
5. Clientes activos sin `priceLock` que no son de los 5 (si hubiera): toman el precio de lista en su próxima transferencia / re-suscripción. Revisar la lista antes de desplegar.

## Stripe (pendiente, no hecho aquí)

- Las suscripciones vivas siguen cobrando el precio con el que se crearon (`price_data` en línea = un Price propio por suscripción). No hay que tocarlas para mantener 300.
- No hay price IDs: si se pasan a Prices del dashboard, guardar `priceLock.stripePriceId` y usarlo en `createCheckoutSession` en vez de `price_data`; los legacy necesitarían un Price de RD$300 aparte.
- No usar "actualizar precio" masivo en el dashboard sobre las suscripciones existentes.
