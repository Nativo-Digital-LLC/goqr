# Fase 4 · Pagos — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** que cada establecimiento se pague solo: suscripción con Stripe Checkout (tarjeta) o transferencia con comprobante revisado por un admin, con el ciclo prueba → activo → pausado manejado por el servidor.

**Architecture:** Functions es la única fuente de verdad de `billing`/`isActive`: callables para abrir Checkout y el portal, un webhook de Stripe (firma verificada, idempotente), un trigger y un callable para transferencias, callables de admin y una función diaria. Web muestra el plan, el pago por transferencia, las páginas de resultado del checkout, el admin y el alta de un segundo local. Stripe se llama con `fetch` (sin SDK).

**Tech Stack:** Functions Node 22 + firebase-functions v2 + Resend (ya instalado); Web React 18 + Vite + shadcn + react-hook-form/zod + sonner; Stripe REST API (Checkout, Billing Portal, Webhooks).

**Spec:** `Web/docs/superpowers/specs/2026-11-19-goqr-relaunch-design.md` (secciones Datos, Reglas, Pagos, Decisiones del builder check, Respuestas del usuario). Diseño: `Web/docs/design/{BillingPlan,BillingActive,BillingTransfer,CheckoutSuccess,AdminTransfers,AdminClients}.dc.html`.

## Global Constraints

- Ramas `fase-4` en **Web** (desde `master`) y en **Functions** (desde `main`). Push a `master`/`main` despliega solo: **no hacer push** hasta que el usuario lo apruebe.
- **Functions tiene trabajo sin guardar del usuario** (`functions/package.json`, `package-lock.json`, `src/connection.ts`, `src/modules/images.ts`, `src/modules/products.ts`, `src/helpers.ts`, `src/types/`): nunca editarlos, añadirlos al commit ni hacer stash/checkout/reset. `git add` solo rutas exactas. Importar de `connection.ts` sí se puede.
- **Sin dependencias nuevas** en ningún repo. Stripe por `fetch` a `https://api.stripe.com/v1` con `Authorization: Bearer <STRIPE_SECRET_KEY>` y cuerpo `application/x-www-form-urlencoded`.
- Secretos por `.env` que arma el workflow desde GitHub secrets (como `RESEND_API_KEY`): se añaden `STRIPE_SECRET_KEY` y `STRIPE_WEBHOOK_SECRET`. No Secret Manager. Leer con `process.env`.
- Precios por establecimiento, ITBIS incluido. DOP: mensual RD$300, anual RD$2,520, de por vida RD$11,000. USD (solo transferencia a EE. UU.): US$5, US$42, US$185 (pendientes de confirmar; una constante por repo, `PLANS`). En Stripe los montos van en centavos (DOP 30000 / 252000 / 1100000).
- Tarjeta: mensual y anual = Checkout `mode=subscription`; de por vida = Checkout `mode=payment`. Toda sesión lleva `metadata.establishmentId` y `metadata.plan` (y en suscripción también `subscription_data.metadata`). Precios con `price_data` en línea (`product_data.name` "GoQR · Plan mensual|anual|de por vida"), sin productos creados en el panel de Stripe.
- El cliente nunca escribe `billing`, `isActive` ni `userId`. Solo Functions (Admin SDK).
- `billing.status`: `trialing | active | past_due | paused | canceled | legacy`. `legacy` nunca se toca automáticamente. `isActive` = `status ∈ {trialing, active, past_due}`.
- Admin = custom claim `admin: true`. Callables de admin rechazan sin la claim (`permission-denied`).
- Sin correos al dueño en esta fase (son la fase 5). Único correo: aviso interno a `contacto@goqr.com.do` cuando llega un comprobante (Resend, `no-reply@goqr.com.do`, texto simple).
- Texto visible en español (RD) con acentos; contacto `mailto:contacto@goqr.com.do` (GoQR no tiene WhatsApp). Web: tabs, tokens, `PanelHeader`, botones con `loading`, `sonner`, `Dialog` de shadcn. Hooks `[handler, loading, error]`.
- Pruebas: lógica pura con vitest en ambos repos. UI se verifica en navegador por el controlador donde se pueda.
- Commits terminan con `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. El webhook llega dos veces, fuera de orden o con un evento que no es nuestro (sin `metadata.establishmentId`): no duplica facturas, no retrocede un estado más nuevo y responde 200 a lo que ignora. → Task 3 (`stripe-events/{id}` + `applyStripeEvent` puro con pruebas de repetición y orden).
2. Dueño con dos establecimientos paga uno: solo ese cambia; el segundo local nunca tiene prueba (empieza `paused`) y puede pagarse desde Plan y pagos. → Tasks 3, 6, 11.
3. Transferencia con monto distinto, USD o sin comprobante: el admin ve monto declarado vs. esperado; aprobar extiende el período desde el vencimiento actual si aún no venció (no desde hoy). → Task 1 (`periodEnd`) y Task 4.
4. Cliente `legacy` o de por vida: la función diaria nunca lo pausa y Checkout no le abre una segunda suscripción. → Tasks 1, 3, 4.
5. Un dueño intenta leer comprobantes o transferencias ajenas, o crear una transferencia ya aprobada: las reglas lo impiden. → Task 5 (reglas) y prueba manual en emulador si está disponible.
